## 2. Validation / Model-Selection Methodology

### Inspection of `train.py` (the actual implementation)

**Checkpoint selection:** `train.py:195-209` — saves `best.pt` when `val_loss < best_val_loss`. This is the validation loss on the held-in validation set (original val minus same-date recordings). The held-out cluster is never consulted.

**Early stopping:** `train.py:213-215` — triggers when `patience_counter >= early_stopping_patience` (10). Based solely on val_loss plateau.

**Val loss computation:** `train.py:162-178` — runs the model on `val_loader` after each epoch. The `val_loader` is built from `split_dir / "val.csv"`, which for each run is the modified validation CSV (excludes same-date recordings).

### Answers

| Question | Answer |
|----------|--------|
| Is the original Experiment 1 val split used? | NO — each run uses a modified val split (excludes same-date recordings) |
| Are fixed epochs used? | NO — early stopping with patience=10 on val_loss |
| Is held-out cluster consulted during training? | NO — only val_loss is monitored |
| Is held-out cluster consulted during checkpoint selection? | NO — best.pt is selected by val_loss |
| Is threshold 0.65 fixed before execution? | YES — set in config, not tuned per-run |
| Can held-out cluster data influence training indirectly? | NO — train CSV is pre-generated and excludes held-out; val CSV excludes same-date |
| Is the held-out cluster consulted for HP selection? | NO — no HP search; exact Experiment 1 config |

### Methodology summary

- **Training:** original TRAIN minus held-out cluster (via pre-generated CSV)
- **Model selection:** early stopping on val_loss (modified val set, excludes same-date recordings)
- **Held-out cluster:** evaluation-only — no data, no metrics, no gradients flow back
- **Official TEST:** untouched, not referenced

**No silent changes to Experiment 1 training procedure.** The only differences from Experiment 1 are:
1. Smaller training set (fewer recordings)
2. Smaller validation set (same-date recordings excluded)
3. Different experiment_id (different data_dir in splits.json)

Everything else (model, optimizer, LR, WD, epochs, patience, augmentation, seed, precision, batch_size, num_workers) is identical.

### Partial date holdout: CORRECT BEHAVIOR (documented)

Three runs have "partial" date holdout — other recordings from the same date exist in training but are NOT held out:

| Run | Date | Held-out recs | Other recs from same date in train | Composition of others |
|-----|------|---------------|------------------------------------|-----------------------|
| `str_holdout_20122022` | 20122022 | 5 stringing | 2 normal (`18_08_37`, `14_53_56`) | PURE_NORMAL |
| `ue_control_10012023` | 10012023 | 8 under-extrusion | 1 normal (`16_47_55`) | PURE_NORMAL |
| `ue_control_05012023` | 05012023 | 7 under-extrusion | 2 normal (`17_47_06`, `12_11_14`) | PURE_NORMAL |

**This is correct.** Clusters are defined by failure-type recordings within a date, not by all recordings from a date. The normal recordings from the same dates remain in training because:
1. They are not part of the stringing/under-extrusion cluster
2. Holding them out would reduce training data without experimental justification
3. The hypothesis is about failure-type domain generalization, not normal-frame domain generalization

The `22122022` cluster IS fully atomic: all 9 train recordings from that date are stringing and all are held out.

### Stringing held-out clusters: SINGLE-CLASS (all failing)

| Run | Frames | Failing | Normal | Binary labels |

| `str_holdout_22122022` | 1,260 | 1,260 | 0 | 100% failing |
| `str_holdout_20122022` | 167 | 167 | 0 | 100% failing |

**Metric implications:**

| Metric | Status | Reason |
|--------|--------|--------|
| Failing recall / FNR | **MEANINGFUL** | Primary metric — fraction of failing frames detected/missed |
| Precision | **DEGENERATE** | Will be 1.0 if model predicts any failing; undefined if model predicts all normal |
| F1 | **MISLEADING** | Depends entirely on precision (which is trivial on single-class data) |
| FPR | **UNDEFINED** | No normal examples to compute false positive rate |
| AUROC | **UNDEFINED** | Requires both classes for ROC curve |
| Accuracy | **MISLEADING** | 100% if model predicts all failing; not informative |

**Reporting rule:** For `str_holdout_22122022` and `str_holdout_20122022`, report ONLY:
- `failing_recall` (= 1 - FNR)
- `fnr`
- Per-recording breakdown (which recordings are missed)

Do NOT report F1, FPR, AUROC, or accuracy for these runs. Label them as "single-class evaluation" in the results.

### Methodological concerns (informational, not blocking)

1. **Single-class held-out evaluation:** Both stringing held-out clusters are 100% failing. FPR, AUROC, F1 are undefined or meaningless. Only failing_recall/FNR are valid primary metrics. This limits the statistical power but does not invalidate the experiment.

2. **Asymmetric sample sizes:** `20122022` has only 167 frames (vs 1,260 for `22122022`). Results from `20122022` will have wider confidence intervals. This is documented in Stage 11A as a limitation.

3. **Modified validation sets:** Each run has a slightly different validation set (different same-date recordings excluded). This is correct methodology but means validation metrics across runs are not directly comparable in absolute terms. Relative degradation (val vs held-out) is the correct comparison.

4. **Partial date holdout for 3 runs:** Normal recordings from the same dates remain in training. This is intentional — we test failure-type domain generalization, not date-level domain generalization.
